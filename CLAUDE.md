# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

- The git root is **not** the Unity project. The Unity project is `sub-terra/` (Unity **6000.5.4f1**, URP 2D, Input System, Tilemap, uGUI + TextMeshPro). All project code/assets live under `sub-terra/Assets/_Project/`.
- `init/`: planning docs and rules. `init/PRD.md` is the source of truth for game design and numbers. `init/rule.md` holds the binding agent/work rules (summarized below). `init/process*.md` covers the A/B role split. `init/prompt-B.md` has the numbered "Prompt-B" task specs.
- `docs/`: `INTEGRATION_GUIDE.md` (how the integration scene is wired), `MVP2_WINDOWS_QA.md` (build/QA procedure), `CHANGELOG.md`.
- `work_process/`: per-feature design notes and results, e.g. `work_process/MVP2/UI-fix-markdown-document/prompt-b107-2-result.md`.
- `.agents/skills/ui`, `.agents/skills/ui-ugui`: UI/uGUI skill references used for UI work.
- `*.csproj` / `.slnx` in `sub-terra/` are generated by Unity and git-ignored. Don't edit them.
- `init/rule.md` is the authoritative source for agent/work rules.
  If this file and `CLAUDE.md` conflict, follow `init/rule.md`.
  Read only the relevant sections when needed rather than loading unrelated project docs.

## Running, testing, building

The primary workflow goes through the Unity Editor
(`C:/Program Files/Unity/Hub/Editor/6000.5.4f1/Editor/Unity.exe`).
Batchmode is available for tests when the Editor is closed.
Windows builds must use the project's Unity Editor build menus described below.

- **Play:** always start Play Mode from `Assets/_Project/Scenes/Bootstrap/Bootstrap.unity`. Flow: Bootstrap → MainMenu → SurfaceBase → Mine_Demo_Integration. Playing `Mine_Demo_Integration` directly is forbidden and fails with `Integration scene opened without the Bootstrap runtime`.
- **Tests (editor open):** use the `SubTerra/Tests/Run Edit Mode Tests` and `Run Play Mode Tests` menus, plus per-feature menus such as `Run Prompt-B 106 Player HUD Tests`. When MCP or the editor UI is unavailable, `EditModeTestRunnerCommand` polls for flag files. Create `sub-terra/Temp/subterra-run-editmode.flag` (or `subterra-run-playmode.flag`), then read `sub-terra/Temp/subterra-editmode-results.txt` (or `subterra-playmode-results.txt`). These runners discover every asmdef under `Tests/EditMode` or `Tests/PlayMode`.
- **Tests (batchmode, editor closed):** standard Unity Test Framework CLI. A single test or fixture is selected with `-testFilter`:
  ```
  Unity.exe -batchmode -projectPath sub-terra -runTests -testPlatform EditMode \
    -assemblyNames SubTerra.App.Tests.EditMode -testFilter "SubTerra.App.Tests.UI.FacilityPurchaseFlowStaticTests" \
    -testResults Temp/results.xml -logFile -
  ```
  Batchmode cannot run while the editor has the project open because of the project lock.
- `PrintTestFailuresOnLoad` automatically runs all EditMode tests once per editor session and writes failures to `sub-terra/Library/TestResults/TestFailures.txt`. `sub-terra/TestFailures.txt` and `TestResultLog_V2.txt` are stale artifacts.
- **Windows build:** use the `SubTerra > Phase P > Build Windows > Development | QA | Release` menus (`PhasePWindowsBuildGate`). They validate required scenes, build, zip, and write a SHA256 and `BUILD_MANIFEST.json`.
- **Data:** `SubTerra/Data/Validate Game Data Catalog` checks ID duplication and missing references. Save slots can be inspected or deleted from `SubTerra/Save/*`.
- Player log: `%USERPROFILE%/AppData/LocalLow/DefaultCompany/sub-terra/Player.log`.

## Architecture

### Assembly layering (enforced by asmdefs)

```
SubTerra.Shared          (noEngineReferences: pure C# contracts/DTOs, no UnityEngine)
   ↑
SubTerra.Gameplay.*      (owner A: world simulation, one asmdef per system)
   Power (no deps) ← Player ← Mining ← Structural/Hazards ← Building ← Drone
   Snapshot, IntegrationBridge, DemoWorld sit on top of those
   ↑ (never referenced by App core)
SubTerra.App             (owner B: state, services, UI, save; references only Shared + Unity packages)
   ↑
SubTerra.App.GameplayIntegration  (Scripts/App/Integration: the ONLY place App and Gameplay meet)
```

- `SubTerra.App` must not reference any `SubTerra.Gameplay.*` assembly. Gameplay must not reference `SubTerra.App`. Cross-boundary code goes in `Scripts/App/Integration/`, or talks through interfaces in `Scripts/Shared/Contracts` and DTOs in `Scripts/Shared/DTO`.
- Because `Shared` has `noEngineReferences`, it cannot use `UnityEngine` types. DTOs carry only IDs, counts, coordinates, and values.

### Runtime wiring

- `GameBootstrapper` (Bootstrap scene) is the single `DontDestroyOnLoad` root that owns the global services (catalog, save, scene loading via `BootstrapContracts.cs`). Tests reset it through `ResetInstanceForTests()`.
- In `Mine_Demo_Integration`, `ApplicationRoot/IntegrationRuntimeBinder` connects the **five Shared boundaries** between Gameplay producers and App consumers: `IMiningRewardReceiver`, `IResourceWallet`, `IGameplayEventSink`, `IWorldSnapshotProvider`, `IDroneContextProvider`. `IntegrationContractRegistry` verifies them, and `IntegrationEventFanOut` fans gameplay events out to the bridges. HUD and input stay gated (the `hudCanvasGroup` and `deferredInputBehaviours` fields) until `SaveRuntimeController` finishes the world restore. `docs/INTEGRATION_GUIDE.md` has the full reference table.
- **Save:** local JSON under `Application.persistentDataPath`, schema **v2** (`Scripts/App/Save`). Writes go to a temp file, get validated, then replace the real file with a backup kept. Only deltas (mined, collapsed, built) are saved. Derived values such as power state are recomputed on load. Adding a DTO field requires a safe default for old saves. Changing a persistent ID requires `SaveMigrationService` support.
- **Static data:** ScriptableObjects under `Assets/_Project/Data`, aggregated by `GameDataCatalog`. Code uses stable string IDs (`mineral.copper`, `building.light.basic`, `upgrade.drill.speed`, ...), never display or asset names. Don't hardcode prices, weights, times, or costs.
- **Digger-Bot:** `DroneAnalysisService` is deterministic and rule-based over `DroneContextDto`. The priority order is survival → collapse → gas → power → return → explore. Cloud AI dialogue (`Scripts/App/AI`) is optional and only rephrases text. The template fallback must always work, and no API keys go in the client.
- Gameplay results (collapse, damage, gas, placement) must be deterministic for a given state and world seed.

### Editor builders

Most UI prefabs and scene wiring are generated by editor "builder" scripts in `Assets/_Project/Editor/DataValidation` and `Scripts/Gameplay/*/Editor`, exposed as `SubTerra/UI/...`, `SubTerra/MVP2/...`, and similar menus named after the Prompt-B number. When changing generated UI, update the builder and re-run it rather than hand-editing prefab YAML. Builders must target explicit constant prefab/scene paths only. Never iterate over and save every prefab or open scene.

## Rules that matter most (from `init/rule.md`)

- **UI change scope must match the request exactly.** Before committing, check `git status` / `git diff --stat`. Unless the task names them explicitly, revert with `git restore` any incidental changes to `Prefabs/UI/SurfaceBasePanel.prefab`, `MainMenuPanel.prefab`, `InventoryPanel.prefab`, `SaveSlotPanel.prefab`, `Scenes/App/SurfaceBase.unity`, `Scenes/App/MainMenu.unity`, and `Fonts/*_SDF.asset`. Regenerating TMP font atlases dirties many prefabs, so don't do it unless that is the task.
- Commits that change `Mine_Demo_Integration.unity` scene YAML are kept separate from feature commits. After builder re-runs, verify the `IntegrationRuntimeBinder` references.
- Don't edit `ProjectSettings/*`, `Packages/manifest.json`, or `packages-lock.json`, and don't bump Unity or package versions. Move or rename assets only in the Editor so `.meta` GUIDs are preserved. Scenes and prefabs are text-serialized, but edit them through the Editor API, not raw YAML.
- C# conventions: use `if (obj != null)` instead of `?.` / `??` on `UnityEngine.Object`. Wrap key binding/init methods (`WireContracts`, `Start`) in try/catch that logs the cause. Put pure logic in plain C# classes so it is EditMode-testable, and keep MonoBehaviours thin. Comments are sparse and in Korean where needed. No per-frame logs.
- Never commit without the user's consent. No destructive git commands. Never print or transmit save files, secrets, or local paths.
- Commit messages are Korean and conventional-prefixed, referencing the prompt number when applicable, e.g. `feat: 퀘스트 UI ... (프롬프트 B-107-1 반영)`. Branches: feature branches with PRs into `main`; never push to `main` directly.
- For UI work, use the installed Unity/UI skills when applicable.
  For existing uGUI screens, preserve the current hierarchy and visual language
  unless the task explicitly requests a redesign.
  Do not load unrelated skills or project documentation.
