# 업그레이드 트리 UI 개편 — Prompt-B 118 작업 명세

| 항목 | 내용 |
| --- | --- |
| 기준 | `Nobamb/sub-terra` / `MVP2-fix44`의 `init/prompt-B.md` 118번 |
| 대상 | 업그레이드 창, 단계별 해금 조건, 구매 검증 및 상태별 UI 연출 |
| 목표 | 드릴 속도를 중심으로 성장 경로와 구매 상태를 읽을 수 있는 Sub-Terra식 트리 UI |
| 우선 규칙 | `CLAUDE.md`, `init/rule.md`와 해당 문서가 안내하는 세부 규칙을 먼저 확인한다. |

## 1. 현재 문제와 작업 목표

- 기존 상단 분야별 탭과 단순 목록 중심 구성을 트리와 우측 상세 패널로 재설계한다.
- 기존 HUD·퀘스트창·시설 건설창·인벤토리·지상 기지 UI의 시각적 방향성을 참고한다.
- 정보 계층, 패널 비율, 노드 배치와 연결선은 실제 항목 수에 맞춰 자유롭게 조정한다.
- 변경할 게임 규칙은 **업그레이드 해금 조건**이며, 기존 효과·비용·최대 레벨은 유지한다.

## 2. 작업 전 조사

1. 관련 Prefab·Scene·Builder·Script·데이터·저장 구조와 기존 열기/닫기·단축키를 확인한다.
2. 모든 업그레이드의 실제 ID, 최대 레벨, 효과, 비용과 구매 조건을 목록화한다.
3. `ProgressionService`, `ProgressionPanelView/Presenter/Binder`, `UpgradeData`와 저장 경로를 추적한다.
4. 기존 빌더의 생성 범위와 실제 Hierarchy를 확인하고, 변경 전 Game View를 기록한다.
5. 드릴 강화 자원 획득 경로와 심층 구역 해금 등 기존 진행 조건의 의존성을 확인한다.
- 기준 브랜치의 `Upgrade_Drill_Speed.asset`은 최대 **Lv.3**이다. 이 작업으로 늘리지 않는다.
- 비용은 Lv.1 구리 8, Lv.2 구리 10·철 6, Lv.3 철 12·리튬 8이며 기존 값을 보존한다.

## 3. 트리 레이아웃

- 중앙에 **드릴 속도**를 두고 기존 업그레이드를 분야별로 주변에 연결한다.
- **업그레이드 하나당 노드 하나**를 사용하며, 레벨마다 별도 노드를 만들지 않는다.
- 공개된 노드에는 아이콘·짧은 이름·현재 레벨/최대 레벨을 표시한다.
- 트리를 주 영역으로, 선택 항목 상세 패널을 오른쪽에 배치한다.
- 원문의 참고 이미지가 제공되면 연결 구조를 참고하고, 노드 과도한 분산과 선 교차를 피한다.
- 기본 화면에서 주요 노드가 읽혀야 하며 실제 항목 수에 맞춰 간격과 화면 비율을 조절한다.

## 4. 단계별 해금과 실제 구매 검증

- 새 게임에서는 드릴 속도를 기본 공개하고, 기존 비용 조건을 만족하면 구매할 수 있게 한다.
- 드릴 속도 Lv.1~3에 맞춰 주변 항목을 단계적으로 해금하며 같은 단계에 여러 항목을 묶어도 된다.
- 모든 기존 업그레이드는 정상 진행으로 해금 가능해야 하며 항목을 누락하지 않는다.
- 잠긴 업그레이드 없이도 드릴 강화 비용을 마련할 수 있어야 한다. 순환 조건과 진행 막힘을 제거한다.
- 단계별 항목 배정은 실제 자원·진행 의존성 확인 후 확정한다. 추측한 조건을 바로 적용하지 않는다.
- 구현할 전체 항목의 **`항목 / 해금 조건 / 연결 대상`** 표를 작성하고 데이터와 구매 로직에 반영한다.
- 구매 처리에서 비용 차감 전에 해금 여부를 검사하고, UI 표시와 같은 조건을 사용한다.
- 현재 `ProgressionService.TryPurchase`의 비용·레벨 검증에 해금 검증을 연결하고 기존 처리 흐름을 보존한다.

## 5. 블라인드와 상세 패널

- 미해금 노드는 위치·연결 관계만 공개하고 어두운 실루엣, `?`와 자물쇠로 표시한다.
- 이름·실제 아이콘·효과·설명은 숨기며, 선택 시 `드릴 속도 Lv.2 필요`처럼 조건만 안내한다.
- 상세 패널과 툴팁에도 숨겨진 정보가 노출되지 않도록 동일한 공개 여부를 적용한다.
- 공개된 항목은 이름·레벨·짧은 설명·현재 효과·다음 효과·비용·업그레이드 버튼을 표시한다.
- 효과는 실제 명칭과 단위를 사용한다. 원시 수치 `1.22`를 의미 확인 없이 배율 등으로 표시하지 않는다.
- 강화 전후 차이를 읽기 쉽게 배치하고, 미해금·구매 가능·비용 부족·최대 레벨을 문구와 시각으로 구분한다.
- 최대 레벨에서는 구매 버튼 대신 **최대 레벨 달성**을 표시한다.
- 구매 확정 직후 골드·관련 자원·레벨·효과·구매 상태와 새로 해금된 노드를 갱신한다.

## 6. 시각적 구성과 구현 방식

- 어두운 금속 패널, 각진 프레임, 절제된 청록색 발광과 회로 형태 연결선을 활용한다.
- 외곽 프레임과 선택한 노드에 강조를 집중하고 모든 요소에 두꺼운 테두리·강한 글로우를 반복하지 않는다.
- 기존 Unity UGUI/TMP와 프로젝트 에셋을 활용하며 이미지 생성에 의존하지 않는다.
- 텍스트·아이콘·버튼·연결선과 자물쇠·블라인드·발광·파편을 독립 요소로 구성한다.
- 장식과 애니메이션 요소가 버튼 입력을 가로채거나 텍스트를 가리지 않도록 한다.

## 7. 상태별 애니메이션

| 상태 | 요구 연출 | 시간 |
| --- | --- | --- |
| 비용 부족 | 해당 노드 좌우 흔들림, 비용 경고색, 부족 자원명과 실제 부족량 표시 후 원상 복귀 | 0.2~0.4초 |
| 레벨업 성공 | 청록빛이 테두리를 한 바퀴 순환, 짧은 발광과 가벼운 확대·복귀, 새 레벨 표시 | 0.5~0.8초 |
| 신규 해금 | 연결선 청록빛 → 자물쇠 진동·파손 → 블라인드 제거·이름/아이콘 공개 → 청록빛 점등 | 0.7~1초 |

- 부족 상태는 미리 표시하되 구매 시도에 실패 피드백을 제공한다. 실제 구매와 차감은 차단한다.
- 골드 이외의 비용도 해당 자원 기준으로 안내하고, 성공 연출은 기본 선택 강조와 구분한다.
- 파편은 소수만 사용하고 빠르게 제거한다. 동시 해금은 짧은 시차를 두되 전체 조작을 막지 않는다.
- 성공 연출은 실제 구매·신규 해금 결과에만 연결한다. 비용·레벨 확정은 게임 로직이 담당한다.
- 연속 클릭으로 중복 구매나 위치·크기·색상 변형 누적이 생기지 않게 한다.
- 창 닫기·화면 전환 시 연출을 정리하고 재개방 시 정상 상태를 복원한다. 확정 구매는 유지한다.
- 일시정지형 창이면 비스케일 시간을 사용한다. 재개방·로드 시 이미 해금된 노드의 연출은 반복하지 않는다.

## 8. 저장 호환성과 변경 범위

- 기존 세이브에서 구매한 업그레이드의 레벨·효과·저장 ID를 보존하고 새 조건 때문에 다시 잠그지 않는다.
- 새 게임과 기존 세이브의 공개·구매 상태가 일관되게 복원되도록 한다.
- 업그레이드 UI와 필요한 해금 데이터·구매 검증·저장 호환 처리·관련 검증에 변경을 한정한다.
- 기존 입력·열기/닫기·단축키·효과·비용·최대 레벨과 그 외 게임 로직을 유지한다.
- 관계없는 UI·시스템·공용 에셋, `ProjectSettings`, `Packages`, Unity/패키지 버전을 수정하지 않는다.
- Scene/Prefab은 규칙에 따른 Editor·Builder 경로로 처리하고 수동 YAML 편집과 광범위 재생성을 피한다.
- 변경을 쉽게 되돌릴 수 있도록 파일 범위를 제한하고 기존 `.meta` GUID를 보존한다.

## 9. 검증과 결과 보고

1. 실제 Game View에서 새 게임의 중심 노드·초기 블라인드·상세 패널과 기본 가독성을 확인한다.
2. 드릴 Lv.1~3의 단계별 해금, 전체 항목 도달 가능성 및 강화 자원 획득에 진행 막힘이 없는지 확인한다.
3. 미해금 직접 구매 차단, 정보 비노출, 비용 부족 시 무차감·실패 연출, 최대 레벨 표시를 검증한다.
4. 구매 직후 수치 갱신, 성공·동시 해금 연출, 연속 클릭과 일시정지 중 재생을 확인한다.
5. 연출 도중 닫기·재개방, 저장 후 재실행, 기존 구매 항목 보존과 해금 연출 미반복을 검증한다.
6. 관련 테스트와 변경 diff를 확인하고 다른 UI·진행 로직의 회귀 및 범위 밖 변경 여부를 점검한다.
- 변경 파일, **최종 해금 조건표**, UI 구성과 디자인 의도, Game View 결과, 검증 결과·남은 제한을 보고한다.
